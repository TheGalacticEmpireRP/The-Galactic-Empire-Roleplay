# Activate member email alerts

This update adds email alerts when support staff send a **public reply** to a ticket. New and existing tickets support them. Members enter their email and confirm an emailed link before alerts begin. Staff notes, member messages, assignments and status-only changes do not send email.

The code is ready, but email delivery requires your sending account to be configured and the updated portal to be deployed. No real email has been sent as part of the automated tests.

## 1. Connect the sender

1. Create or sign in to [Resend](https://resend.com/).
2. In [Domains](https://resend.com/domains), add a domain you own and complete the DNS verification shown by Resend. A subdomain can be used. This does not change the support website's `tge-support.pages.dev` address.
3. Create an API key with permission to send emails for that domain.
4. Open this repository's **Settings → Secrets and variables → Actions → New repository secret** and add:

   | Secret name | Value |
   | --- | --- |
   | `RESEND_API_KEY` | The API key generated by Resend |
   | `SUPPORT_EMAIL_FROM` | A sender on your verified domain, such as `TGE Support <support@your-domain.com>` |

Keep the existing Cloudflare and owner sign-in secrets. Add the email settings to GitHub secrets, not to public source files or chat. The deployment workflow transfers them to server-only Cloudflare settings.

Resend requires a domain you control for production sending. Your Cloudflare `pages.dev` subdomain, a `github.io` address, and a personal Gmail address cannot serve as your verified sending domain. The default `onboarding@resend.dev` sender is for testing, not community-wide notifications. Check the provider's current quotas before activation.

## 2. Publish the update

Open **Actions → Deploy Imperial Support to Cloudflare → Run workflow**. Select `main` and keep the existing project name **`tge-support`**. This applies the additive `0004_member_email_notifications.sql` migration and publishes the updated portal. Existing tickets, staff accounts and receipt keys are preserved. The workflow is started manually; committing this update runs the checks without publishing it.

If you deploy locally, provide the same settings in your environment and use the existing deployment commands. The Worker uses `RESEND_API_KEY`, `EMAIL_FROM` and `SUPPORT_BASE_URL`; the provisioning script sets them from the GitHub settings above. Preview deployments receive no production credentials or database.

## 3. Verify the complete flow

1. Open a test ticket and enter an inbox you control, or open an existing ticket with its private receipt and select **Enable email alerts**.
2. Open the confirmation email and select **Confirm email alerts**. Confirmation links expire after 24 hours and can only be used once. They grant no ticket access.
3. Sign in to the staff console and send a public reply. Confirm that the member receives a **You have a new support reply** email containing the reference and a **View your ticket** link.
4. Confirm that a private staff note sends no email. The member still uses their private key to open the conversation. Email alerts contain no conversation text, evidence or private access keys.
5. Inside the member's conversation, check **Email reply alerts** to change the address, resend confirmation or turn alerts off. An address change needs a new confirmation. No old alerts are sent retroactively on confirmation.

## Failed delivery

The staff reply is saved before sending an alert. If the email service rejects the request or is unavailable, staff see a failure notice and can use **Retry email alerts** in that ticket. Requests time out after eight seconds. Retry processes up to three pending alerts at a time and uses a per-message idempotency key and a send lease to prevent concurrent duplicates.

Pending alerts can be retried up to ten times during the first 23 hours. This stays inside Resend's 24-hour idempotency window. There is no background scheduler; the normal attempt occurs with the staff reply, and further attempts are explicitly triggered by staff. Successful API acceptance does not guarantee inbox delivery. Check Resend's delivery logs and the recipient's spam folder when needed. Replies to the notification email are not imported into the ticket.

## Validation

Type checking, production builds and automated tests cover verification, recipient isolation, public-reply-only alerts, existing-ticket opt-in, disabling alerts, retry failures, concurrent delivery and deployment secret handling. The local Cloudflare/D1 runtime checks apply the new migration alongside the existing schema. Browser visual QA and real email delivery still require a live walkthrough after configuration.
